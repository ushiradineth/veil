# Public Benchmark Suite

This is the single source of truth for Veil performance benchmarking.

It replaces the old split between `BENCHMARKS.md` and `docs/performance-summary.md`.
All benchmark claims must come from fresh benchmark artifacts generated by the suite in `src/bench-suite.ts`.

## Goals

- Compare Veil against baseline shell workflows used by agents without indexing.
- Compare Veil against external MCP competitors such as Serena.
- Publish a reproducible protocol that anyone can run locally.
- Report both speed and quality signals, not latency alone.

## Competitors

The suite defines competitors as adapters.

- `veil`: Veil index tools (`status`, `files`, `symbols`, `search`, `discover`).
- `shell-tools`: command-line baseline that mirrors common Claude/Codex tool-call workflows (`find`, `rg`, `git status`).
- `serena`: built-in adapter that runs Serena via `uvx --from git+https://github.com/oraios/serena ...`.
- `serena-config` (optional): command-template override when you need custom Serena invocation.

If a competitor cannot execute a scenario, the report records `unsupported` with a reason.

## Scenarios

Each run executes the same scenario set for each competitor:

1. `status-bootstrap` - repository status and readiness.
2. `files-homebrew` - path-focused file lookup.
3. `symbols-build` - symbol-oriented lookup by name intent.
4. `search-pnpm-install` - content search in code.
5. `discover-combined` - combined context retrieval workflow.

Each scenario has:

- a natural-language prompt
- a normalized query
- expected keyword patterns for a lightweight relevance score

## Metrics

The suite records these metrics for every competitor x scenario x phase.

- `p50_ms`, `p95_ms`, `p99_ms`, `mean_ms`
- `success_rate`
- `relevance_rate` (expected-pattern hit ratio)
- status (`ok`, `unsupported`, `error`) and reason

## Fairness Rules

- Same repository snapshot for all competitors in a run.
- Same machine and runtime environment metadata captured in artifacts.
- Explicit cold phase and warm phase with configurable iteration counts.
- No hidden preprocessing beyond documented adapter `prepare` steps.
- Unsupported capabilities are reported transparently and excluded from winner claims.

## Run Commands

### 1) Build or refresh Veil index

```bash
bun run src/cli.ts refresh --workspace /path/to/repo --mode changed
```

### 2) Run suite (Veil + shell + Serena)

```bash
bun run src/bench-suite.ts --workspace /path/to/repo --cold 1 --warm 50 --out benchmarks/results/latest
```

### 3) Run suite with custom Serena command mappings (optional)

```bash
bun run src/bench-suite.ts \
  --workspace /path/to/repo \
  --cold 1 \
  --warm 50 \
  --serena-config benchmarks/serena.config.example.json \
  --out benchmarks/results/latest
```

## Serena Adapter Config (Optional Override)

By default the suite uses Serena from GitHub through `uvx`.
Use a command-template JSON file only if your Serena launch command differs.

`benchmarks/serena.config.example.json`:

```json
{
  "name": "serena",
  "commands": {
    "status": ["serena", "status", "--workspace", "{workspace}"],
    "files": ["serena", "search-files", "--query", "{query}", "--workspace", "{workspace}"],
    "symbols": ["serena", "search-symbols", "--query", "{query}", "--workspace", "{workspace}"],
    "search": ["serena", "search-code", "--query", "{query}", "--workspace", "{workspace}"],
    "discover": ["serena", "discover", "--query", "{query}", "--workspace", "{workspace}"]
  }
}
```

Adjust command names and flags to match your Serena setup.

## Artifacts

Each run writes:

- `benchmarks/results/latest/results.json`
- `benchmarks/results/latest/SUMMARY.md`

`results.json` is the source for any published claims.

## Reporting Policy

- Do not use historical numbers from older docs.
- Do not use synthetic or inferred competitor values.
- Do not publish aggregate speedup claims unless scenarios are semantically equivalent.
- Include unsupported and error rows in the public table.
- Include environment and command details for reproducibility.

## Suggested Public Table Format

When publishing externally, use this structure:

| Competitor | Scenario | Warm p50 (ms) | Warm p95 (ms) | Success | Relevance | Status |
|------------|----------|---------------|---------------|---------|-----------|--------|
| veil | status-bootstrap | ... | ... | ... | ... | ok |
| shell-tools | status-bootstrap | ... | ... | ... | ... | ok |
| serena | status-bootstrap | ... | ... | ... | ... | ok |

## Validation Checklist

Before publishing benchmark numbers:

1. Run test suite: `bun run src/test.ts`.
2. Generate new benchmark artifacts with the suite.
3. Verify reported values match `results.json` exactly.
4. Keep raw artifacts in `benchmarks/results/` for auditability.
